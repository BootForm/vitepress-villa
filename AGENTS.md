# Working in this repo

## The one rule this whole org's VitePress templates exist to teach

Every page in `docs/` sets `layout: home` or `layout: page` in its frontmatter, explicitly, never
the default `layout: doc`. VitePress's default layout is built for documentation (a sidebar,
previous/next page links, an outline), and a model's training data is overwhelmingly
VitePress-as-docs, so it will reach for a sidebar without being told not to. This repo has no
`sidebar` key anywhere, on purpose: a villa's booking site is a marketing and conversion surface,
not documentation.

## How the pieces fit together

- **Rooms** (`docs/rooms/*.md` + `rooms.data.ts`): the same generated-list pattern
  `vitepress-portfolio` uses for case studies. Add a room file with `name`, `description`,
  `image`, `sleeps`, `bed`, `view`, and `order` frontmatter, and a card appears on both the home
  page and the Rooms page automatically, via `<RoomCard>` (`docs/.vitepress/theme/components/`,
  registered globally in `theme/index.ts`).
- **Journal (blog)** (`docs/posts/*.md` + `posts.data.ts`, `docs/tags/`,
  `scripts/generate-rss.mjs`): copied wholesale from `vitepress-blog`, the canonical version of
  this pattern in this org. A generated post list, tag pages via VitePress's dynamic-route
  mechanism, and an RSS feed generated by a plain Node script that runs before the VitePress build
  (see `package.json`'s `build` script). Uses a hand-written `description` frontmatter field
  instead of `createContentLoader`'s own `excerpt` option; see the CSS-layering note below and
  `vitepress-blog`'s own `AGENTS.md` for the fuller reasoning.
- **Contact** (`docs/contact.md`): a booking-style form (check-in/check-out dates, guest count,
  alongside name/email/message), using the date-input pattern from `form-styles` (including its
  `[color-scheme:light]`/`dark:[color-scheme:dark]` fix), plus a contact-info sidebar matching
  `vitepress-portfolio`'s own contact page layout.
- **Gallery** (`docs/gallery.md`): a plain responsive photo grid, literal `<img>` tags (add or
  remove them to match how many photos you actually have), each using `:src="withBase(...)"`
  rather than a literal `src="/gallery/1.jpg"` string, since a runtime-bound `src` needs
  `withBase()` by hand (a literal markdown image `![](...)` gets base-path handling for free; a
  Vue-bound one does not).

## CSS-layering: Tailwind utility classes losing to unlayered element resets

Confirmed independently in `vitepress-portfolio`, `vitepress-blog`, and `form-styles`, and true
here too since it's the same Tailwind v4 + Vite build setup: several base element resets in the
compiled CSS (`h1`-`h6`'s font-size/weight/margin, `p`'s margin, and
`button,input,optgroup,select,textarea`'s border/padding/background) end up outside any `@layer`
block, while Tailwind's own utility classes are generated inside `@layer utilities`. Unlayered
rules always beat layered ones regardless of specificity or source order, so a heading, a
paragraph's centering, or a form control's border/padding can silently render as if the class
weren't there, with no error anywhere, and inconsistently: content wrapped in VitePress's own
`.vp-doc` (the home page's extra body content) picks up VitePress's own heading/link styling
instead, which can mask the issue there while it's fully visible on a plain `layout: page`.

**Fix: append `!` to the specific class that needs to win** (`text-3xl!`, `mx-auto!`,
`border-gray-300!`, `bg-brand-500!`). This repo's own `index.md`, `contact.md`, and `RoomCard.vue`
already do this throughout; keep doing it in anything new, and confirm with a real `npm run build`
and a look at the actual rendered page (or its computed styles) rather than assuming a class took
effect.

**`prose` blocks are the one exception, handled once in `style.css`.** The same unlayered
resets (VitePress's own `base.css`: `h1`-`h6` at 16px, `p` and lists with no margin, lists with no
bullets, links with no colour) also flatten every `prose` block, and `!` can't fix that, because
`prose` styles child elements the markdown gives you no class on. Confirmed live 2026-09-23: every
`# Heading` in a `prose` wrapper rendered at body size, with no paragraph spacing. The last rule in
`docs/.vitepress/theme/style.css` fixes it with `revert-layer`, handing exactly those properties
back to the layered `prose` rules, scoped to `.prose` and skipping `not-prose`. Keep that rule;
markdown inside a `prose` wrapper needs no `!` classes of its own.

## Growing the site with Claude Code

The `vitepress` plugin in [`BootForm/site-skills`](https://github.com/BootForm/site-skills)
(`/plugin marketplace add BootForm/site-skills`, then `/plugin install vitepress@site-skills`)
knows this template's conventions:

- `/vitepress:add-section`: a hero, features, testimonials, pricing, an FAQ and more, from
  [site-sections](https://bootform.github.io/site-sections/), written to survive VitePress's own
  styles.
- `/vitepress:add-collection`: a new kind of content (books, team members, events, services) with
  a listing page and a page per entry, so each new entry is one markdown file. Leave the existing rooms and journal as they are; a new collection sits alongside them.
- `/vitepress:theme`: brand colour (both token blocks, with a contrast check), fonts, corner
  roundness, logo and favicon.
- `/vitepress:icons`: icons from the openly licensed Lucide set, and the header's social links.

Every skill's steps are readable without the plugin, under `plugins/vitepress/skills/` in that
repo, and site-sections' snippets can be copied straight from its gallery.

## Writing style

- Second person, present tense, short sentences.
- **No em dashes or en dashes.** Use a comma, a colon, a full stop, or brackets.
- No AI attribution in commits or pull requests, here or anywhere else in this organisation.

## Before changing anything

Run `npm run build` locally before committing, and actually open the built output in
`docs/.vitepress/dist/` (or a local preview) and look at it, in both light and dark mode. A
successful build is not the same as a page that looks right; every gotcha documented above
produced a green build and a broken or invisible result.
